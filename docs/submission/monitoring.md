# 运行监控与 TensorBoard

## 使用

启动新版控制服务后，进入“监控”。全站导航下方整个视窗直接显示 TensorBoard，不再展示外层摘要、节点表或协议详情卡片，也不占用页脚空间。默认实验沿用已有选择；尚未选择时优先使用当前运行任务，否则按创建时间选择最新实验，不依赖接口列表顺序。停止任务、导出记录和选择实验通过“看板”操作。训练与资源曲线统一在原生 TensorBoard 中查看。

- 默认打开原生 Time Series 面板，筛选当前实验及其节点、主机日志，初始平滑系数为 0。可在原生面板调整平滑、缩放、横轴和 Runs 选择；筛选同时兼容 Windows 与 Linux 的日志目录分隔符。
- 原生“实验记录”列表按日志路径区分实验、节点与主机。默认筛选当前实验；清空“筛选实验（正则表达式）”后可以勾选多个已有实验比较，输入节点或主机路径也可缩小范围。进入监控时，后台顺序导出其余历史实验，每次只处理一个，不会重新执行历史任务；单个导出失败不会阻塞其它历史实验。
- 当前实验日志约每 10 秒同步；TensorBoard 原生自动刷新默认每 30 秒查询新点，显示延迟还受两者的实际完成时间影响。首次使用时仅在未设置过原生自动刷新偏好时启用自动刷新，已有开关、周期及其他设置保留；可在原生顶部修改。后台同步不重载 iframe，保留正在进行的筛选、平滑与缩放操作。没有实验时也可打开 TensorBoard 查看已有日志；没有日志则显示原生空数据提示。
- 资源目标采样间隔为 5 秒；硬件读取与网络延迟会影响实际间隔，应以采样时间为准。页面请求不会现场调用节点或传感器，也不会为显示曲线重复拉取整个节点历史。
- 旧实验仅补录已有证据。未采集的本地 epoch、节点资源不会生成曲线，也不会用当前部署补全历史。

原生控件、指标分组和已知图表标题以中文显示，标题包含单位。汉化资源由同源服务提供并随源码和安装包打包，无需外部 CDN。实验标识、节点标识、原始 tag、筛选表达式和曲线数值保持原值；可继续用原始英文 tag 搜索或导出。窄屏下设置面板以浮层显示，可用原生关闭按钮收起后查看曲线。

“筛选指标”仍匹配原 tag，例如 `^evaluation/` 查看按全局轮次对齐的全局测试和客户端训练比较曲线、`^training/` 查看客户端逐 epoch 训练集指标、`^protocol/` 查看阶段耗时、`^communication/` 查看通信量。面板只展示关键指标白名单，所有范围合计最多 40 种图表；同一指标中的多个实验或节点使用多条曲线比较，不为每个客户端重复创建指标。只有记录中实际存在的指标才会生成图表，所以旧实验或 CPU 实验通常少于 40 张。

显示筛选在 TensorBoard 服务的数据读取层执行，同时约束标签发现与曲线读取；旧实验已经导出的逐内核、配置和诊断指标立即从面板隐藏，无需删除或重写历史日志。完整原始实验记录、监控采样与已有事件文件保留，隐藏指标仍可用于离线诊断，不影响原有记录导出。

## 指标口径

| 分组 | 最多图表数 | 面板保留的内容与口径 |
| --- | --- | --- |
| 全局测试集 | 2 | `evaluation/accuracy` 为准确率（0–1），`evaluation/cross_entropy` 为交叉熵，横轴均为全局轮次。根实验曲线是聚合模型在实验配置的 MNIST / CIFAR-10 测试子集上的评估；`nodes/clientN` 曲线是对应客户端每轮最后一个本地 epoch 的训练集评估。同图按原生运行颜色区分。初始全局评估存在时记为第 0 轮，客户端不补第 0 轮；正在执行的轮次不提前生成比较点 |
| 本地训练集 | 3 | 每个客户端实际训练分区的准确率、交叉熵，以及本地 epoch 训练耗时。`training/accuracy` 为 0–1，`training/cross_entropy` 为交叉熵，`training/epoch_s` 为秒。评估的是量化前、训练后攻击变换前的模型；标签翻转使用实际训练标签，不能与全局测试集指标混为一谈 |
| 轮次执行 | 1 | `round/duration_s`：单轮实际墙钟耗时，秒；用于直接比较各轮执行速度 |
| 整个任务 | 1 | `task/duration_s`：任务累计墙钟耗时，秒；仅任务终态在最后完成轮次记录，包含启动与收尾，不作为每轮耗时 |
| 协议 | 6 | `protocol/stages/` 下的 `dkg_s`、`client_stage_s`、`validation_s`、`aggregate_key_s`、`partial_decryption_s`、`combine_and_confirmation_s`：建钥、客户端提交、验证、聚合密钥派发、部分解密、合并确认的墙钟耗时，秒。隐藏重复父项 `aggregation_s`、验证子项及诊断收集计时 |
| 证明 | 3 | `proof/generation/proof_gen_s` 为客户端证明生成耗时；`proof/verification/proof_verify_total_s` 与 `proof/verification/inner_product_total_s` 为各边缘节点本轮所验证客户端的累计证明验证、累计内积计算耗时，秒。同名指标按节点叠加曲线，验证标签不再包含客户端编号；累计用时不是包含通信等待的验证阶段墙钟。只有该项全部客户端计时有效时才生成汇总，缺失或空集合不补零 |
| 聚合合并 | 3 | `combine/combine_total_s`、`combine/combine_proof_verification_s`、`combine/combine_numerators_s`：各参与者合并总耗时、部分解密证明核验、分子计算耗时，秒。各节点使用同名图表的不同曲线；不重复展示协议分组中的各节点最大值或缓存诊断 |
| GPU 密码计算 | 6 | `gpu_compute/totals/` 下的 `host_wall_ms`、`kernel_ms`、`upload_ms`、`download_ms`、`sync_ms`、`scheduler_wait_ms`：本进程逐轮成功调用墙钟、CUDA 内核、上传、下载、主机等待及调度等待，毫秒。隐藏逐内核、任务累计、配置、静态资源和调试计数，图表数量不随内核种类增长 |
| 客户端筛选 | 6 | `clients/` 下的通过、拒绝、连带剔除、未成功返回、被接纳的恶意客户端、被拒绝的诚实客户端数量，个。恶意与诚实身份来自实验配置的已知身份，只有记录存在时才展示 |
| 主机 | 4 | 每台机器的整机 CPU 利用率、内存占比、GPU 利用率和已用显存。前三项为百分比，显存为字节。包含其他应用负载；GPU 不分摊给节点，不重复相加。单机复用主控采样，远端每台机器选一个节点采集 |
| 实验进程 | 2 | `processes/cpu_percent` 与 `processes/rss_bytes`：节点及已核验子进程的 CPU 利用率和 RSS 合计。CPU 按逻辑核数归一化到整机容量的 0–100%；RSS 单位为字节，共享页可能重复计算，不能与系统内存直接相加 |
| 监控额外开销 | 1 | `monitoring/metrics_eval_s`：各客户端本轮监控评估的额外耗时之和，秒；不加入原训练计时。并行时不是本轮新增墙钟时间 |
| 协议通信 | 2 | `communication/round_bytes` 为单轮协议通信量；`communication/task_total_bytes` 为终态整个任务通信量，均为应用层序列化 RPC 请求与响应字节，不含完整 TLS/HTTP/TCP 帧。监控通信单独统计，不计入协议通信量 |

本地训练曲线累计 step 为 `(全局轮次 − 1) × local_epochs + 本地 epoch`。本地轮次编号、所属全局轮次、样本数、可信参数加载、线程数、硬件频率/温度/功耗、磁盘容量、全局模型范数和其余细分计时仍按原方式记录，面板不为这些辅助字段单独画图。需要诊断时读取原始实验结果、资源采样或事件文件。

全局测试集的两张图同时用于对照客户端训练效果，不增加图表种类。客户端点仅从已完成轮次中实际记录的末次 epoch 导出，并核对该实验的 `local_epochs`、所属轮次和累计 step，按全局轮次对齐；不会把部分 epoch、事件接收顺序或当前部署当作历史依据。原生图例中的根实验代表全局测试，`nodes/client1`、`nodes/client2` 等代表各客户端训练集，可勾选或筛选曲线；原始运行标识和颜色设置保留。逐 epoch 的完整训练变化仍在“本地训练集”分组查看。

全局测试与客户端训练使用不同模型和不同评估集，数值不能视为同一测试集上的直接优劣。客户端使用自身实际训练标签，标签翻转实验可能已经改变这些标签；记录在模型输出攻击变换和量化之前。没有采集客户端 epoch 指标的旧实验仍只有全局曲线，不补造客户端数据。

父子阶段和并行节点耗时不可直接相加。尤其合并总耗时已包含证明核验、分子计算；GPU 内核、主机同步等待和调用墙钟也会重叠。通信的单轮值与整个任务值统计范围不同，任务值包含轮次之外的启动等通信；隐藏可由逐轮值计算的重复累计曲线。

GiB = 1024³ 字节。TensorBoard 资源 scalar 的 step 是采样序号，可切换实际时间/相对时间查看采样时间。缺失值不写入 TensorBoard；0 仅表示实际测得零。首个进程 CPU 读数没有相邻时间差，通常为空；两次采样间退出的短命工作进程可能未被完整计入。

节点、角色、机器、地址和客户端归属在实验启动时保存。主机分组以这份部署快照为准，每组一份整机数据；远端节点只上报本机资源，不把主控采样当作集群总量。遥测通过已有认证 RPC，以独立通信客户端、短锁和有界采集线程池运行；训练或证明占用业务锁时，读取已有监控缓存仍可响应。节点断连后重试并按事件序号增量补取、去重，采集或日志写入失败只报告监控状态，不中止或重复业务计算。

## 安装与保存

TensorBoard 2.21.x 已加入基础依赖。已有环境在项目根目录执行：

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-lock.txt
Set-Location web
npm.cmd ci
npm.cmd run build
Set-Location ..
```

再按部署手册重启控制服务。新环境使用原有部署脚本即可。离线环境需在联网准备机用新版依赖重新生成离线包；旧 wheelhouse 可能缺少 TensorBoard、protobuf、grpcio 等新增依赖，不能只复制本次源码后继续沿用旧离线包。

日志与实验结果分开保存：

```text
runtime/tensorboard/<run_id>/events.out.tfevents.*       全局测试与兼容资源指标
runtime/tensorboard/<run_id>/nodes/<node_id>/           节点训练、进程资源标量
runtime/tensorboard/<run_id>/machines/<machine_id>/     每台机器的整机资源标量
runtime/monitoring/<run_id>/                           持久化增量监控事件
runtime/results/<run_id>/result.json                   实验结果、轮次及监控摘要
```

节点端另保留带序号的遥测事件供断连补取。资源原始采样独立保存，`GET /api/runs/{run_id}/monitor` 保留本次实验的节点、主机最新指标和状态摘要接口；满屏监控使用 TensorBoard 原生读取，不再展示独立节点表。备份需保留对应实验结果、监控事件及 TensorBoard 日志，不要混入 `runtime/keys`。

客户端比较曲线从 `runtime/monitoring/<run_id>/` 的独立 epoch 事件补录，兼容旧记录中保存的轮次训练指标。业务 `train` RPC 不传输监控字段，因此轮次摘要里的 `client_training_metrics` 为空不代表没有采集。最终 epoch 早于轮次完成到达时，导出器暂存该点，待轮次完成再发布；晚到、重启或日志写入失败后均可从持久化事件恢复，重复同步不会重复写点。补录只追加 TensorBoard 日志，不回写实验结果、不重复训练。既没有独立事件也没有轮次训练指标的历史实验仍只显示已有全局曲线。

TensorBoard 使用控制服务的同源 `/tensorboard/` 路径，复用 8765，不新增 6006 监听端口。前端开发服务也配置了路径代理。日志只导出公开标量，不写入私钥、客户端原始样本或单个客户端模型梯度。

未安装或无法加载 TensorBoard 时，覆盖层显示原因、重试与记录导出入口；没有实验时提供部署入口，不恢复自绘曲线。磁盘满或事件写入失败时，检查空间和目录权限后重试补录已有证据；后台同步暂时失败会保留已加载面板及已有日志，以浮动提示显示同步异常。

## 验证方式

通过 TensorBoard event reader 核对初始评估、逐轮测试、累计本地 epoch 和资源标量；重复拉取、补录及服务重启不得重复记录同一 scope/tag/step。验证 NumPy、Torch 开关 epoch 回调后的最终权重一致，独立评估值与记录一致。控制与节点测试覆盖业务锁并发、单机/模拟三机分组、断连恢复、关闭清理和历史未记录状态。前端测试覆盖精确筛选、单位与缺失值、自动加载、取消旧请求、后台不重载、错误恢复和真实组件渲染；真实浏览器验收须另核对桌面及窄屏布局。
